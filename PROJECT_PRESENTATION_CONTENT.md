### Slide 2: Abstract
- **Core Problem:** Traditional centralized CDNs suffer from edge server imbalances, latency spikes, and ungraceful failures under sudden load surges.
- **Proposed Solution:** A decentralized, multi-tier Edge CDN featuring:
  - Multi-parameter QoS routing taking into account latency (EWMA), active connections, and cache locality.
  - Independent edge storage with Least-Recently-Used (LRU) capacity eviction.
  - Fail-safe origin fallback ensuring 100% request availability.
  - Live interactive dashboard simulating concurrent multi-client traffic (up to 100 clients).
- **Key Findings:** Caching yields sub-millisecond response times (<5 ms) compared to origin fetch (~45–90 ms), while dynamic load re-weighting protects congested nodes.
- **Speaker Notes:**
  > "In summary, our project designs and implements a portable, multi-edge CDN architecture. By decoupling edge caching from origin storage and orchestrating requests through a mathematical QoS metric, we drastically reduce tail latencies, eliminate single points of failure, and dynamically shift load away from degraded nodes."

### Slide 3: Introduction & Problem Statement
- **Background:** Exponential growth in web video, high-resolution multimedia, and interactive web services.
- **Challenges in Traditional Content Delivery:**
  - **High Propagation Latency:** Endpoints geographically distant from central origin servers face high RTT.
  - **Origin Bottleneck:** Traffic spikes saturate origin CPU and bandwidth.
  - **Static / Round-Robin Routing Deficiencies:** Traditional DNS/round-robin load balancers ignore real-time edge congestion and object locality.
  - **Cache Thrashing:** Unbounded or naive caching leads to disk exhaustion and stale content delivery.
- **Visual:** Comparison graphic showing Single Origin vs Distributed Edge CDN.
- **Speaker Notes:**
  > "Traditional architectures route users blindly using static DNS or simple round-robin algorithms. If an edge node experiences heavy compute pressure or network degradation, clients routed there experience severe lag. Furthermore, if an edge doesn't have the requested asset while another does, naive routers cause an unnecessary cache miss and origin hit."

### Slide 4: Project Objectives
- **Primary Goals:**
  1. **Deploy Distributed Edge Layer:** Stand up 3 independent edge caching processes with local disk isolation.
  2. **Develop QoS-Aware Routing Gateway:** Implement dynamic edge selection incorporating Round-Trip Time (RTT), active load, and cache locality.
  3. **Implement Bounded LRU Cache:** Enforce strict disk capacities (128 MB threshold) with automatic LRU cleanup.
  4. **Build Fault Tolerance & Fallback:** Seamless retry across surviving edges, falling back to origin if all edge nodes are unreachable.
  5. **Real-Time Telemetry Dashboard:** Provide visual tracking of p50/p95 latencies, edge health counters, and a configurable client load generator.
- **Speaker Notes:**
  > "Our primary goals were to create a working, portable system that couples an intelligent decision-making router with self-sufficient edge nodes, wrapped in a live benchmark and telemetry suite to prove its performance under stress."

### Slide 5: Methodology — System Architecture
- **Hierarchical 3-Tier Architecture:**
  - **Tier 1 — Client Layer:** Concurrent HTTP traffic generated by user requests or load simulator.
  - **Tier 2 — Routing & Control Layer (`qos_router.py` :9000):** Probes edge health, computes candidate scores, and handles upstream transparent proxying.
  - **Tier 3 — Edge Layer (`edge_node.py` :8001, :8002, :8003):** Local disk caches (`cache/edge1`, `edge2`, `edge3`) with LRU eviction and hit/miss reporting.
  - **Tier 4 — Origin Layer (`origin_server.py` :5000):** Central authoritative media store (`cdn_images/`).
- **Visual:** Complete architectural flowchart:
  ```
  Client -> QoS Router (:9000) -> Edge Nodes (:8001, :8002, :8003) -> Origin (:5000)
                 ^                             ^
                 |------- Dashboard (:9100) ---|
  ```
- **Speaker Notes:**
  > "As seen in this architecture, clients do not contact edge nodes or origin servers directly; they query the QoS Gateway on port 9000. The router constantly tracks edge health using background probes and selects the optimal path. The live dashboard on port 9100 monitors the entire ecosystem in real-time."

### Slide 6: Methodology — Mathematical QoS Routing Model
- **Dynamic Scoring Function:**
  $$\text{Score} = \text{Latency}_{\text{EWMA}} + (\text{Active Connections} \times 15.0) + (\text{Failure Streak} \times 150.0) - \text{Locality Bonus}$$
- **Components:**
  - **Latency Smoothing (EWMA):**
    $$\text{EWMA}_t = 0.75 \times \text{EWMA}_{t-1} + 0.25 \times \text{Sample}_{\text{ms}}$$
  - **Concurrency Penalty ($15\times$):** Disincentivizes routing to busy edges already handling in-flight requests.
  - **Failure Penalty ($150\times$):** Quickly deprioritizes flaky nodes before heartbeat timeout.
  - **Cache Locality Bonus ($-10,000$):** Massive deduction if the requested asset is verified in the edge's local cache inventory, virtually guaranteeing a cache hit.
- **Overload Degradation:** Degraded edges receive a $0.30\times$ weight reduction (~13% selection vs 43.5% for healthy peers).
- **Speaker Notes:**
  > "The core innovation of our router is this cost function. Rather than guessing, the router calculates a composite score. If an edge already has the file cached, it gets a negative 10,000 point bonus, prioritizing an instant cache hit. If an edge is slow or overloaded, its score increases, deflecting new traffic to faster peers."

### Slide 7: Methodology — Edge Caching & Eviction (LRU)
- **Edge Storage Mechanics:**
  - Isolated cache directories per edge node.
  - Atomic writing via temporary files (`.tmp-*`) to prevent corrupt or partial reads during network interruptions.
- **Least-Recently-Used (LRU) Eviction:**
  - Bounded storage limit: Default 128 MB per edge.
  - When threshold is exceeded, edge queries file access timestamps (`st_atime`) and evicts the least recently accessed objects first.
- **Header Telemetry:**
  - Injects `X-Cache: HIT` or `X-Cache: MISS`.
  - Injects `X-Edge-ID`, `X-Edge-Time-Ms`, and `X-Router-Time-Ms`.
- **Speaker Notes:**
  > "Each edge operates independently. Cache integrity is preserved through atomic writes. When an edge reaches capacity, its LRU eviction policy automatically frees space without disrupting active content delivery. Detailed response headers allow clients and observability tools to inspect every hop."

### Slide 9: Implementation — Fault Tolerance & Fallback Strategy
- **Layer 1: Health Probing & TTL Caching:**
  - Router probes `/health` every 1.5 seconds (`HEALTH_TTL_SECONDS`).
  - Probes timeout aggressively at 600 ms (`EDGE_PROBE_TIMEOUT_SECONDS`) to avoid stalling client pipelines.
- **Layer 2: Multi-Edge Failover:**
  - If the top-ranked edge throws a socket error or HTTP 5xx, the router dynamically removes it and instantly retries the second-ranked edge candidate.
- **Layer 3: Direct-to-Origin Fallback:**
  - If all 3 edge nodes simultaneously go offline, the router routes requests directly to `http://127.0.0.1:5000/files/<filename>`.
  - Clients receive `X-Routed-Edge: origin-fallback` with uninterrupted service.
- **Speaker Notes:**
  > "High availability was a core design requirement. Our three-layer resilience guarantees zero downtime: health probes detect faults in sub-second intervals, client requests fail over transparently between edges, and if all edges collapse, origin fallback kicks in seamlessly."

### Slide 11: Experimental Results — Dynamic Overload & Outage Adaptation
- **Scenario A: Simulated Edge Congestion:**
  - Triggered overload on `Edge 1` via dashboard control.
  - Router detected increased EWMA latency and applied 0.30x penalty weight.
  - Traffic automatically shifted: `Edge 2` and `Edge 3` handled 87% of requests, preventing `Edge 1` collapse.
- **Scenario B: Simulated Edge Outage (Down):**
  - Simulated complete failure on `Edge 2`.
  - Zero dropped requests observed: Router intercepted connection errors and transparently completed transactions via `Edge 1` and `Edge 3`.
- **Visual:** Latency trend chart showing traffic diversion and automatic recovery after lease expiry.
- **Speaker Notes:**
  > "During our stress tests, we deliberately injected edge failures and congestion. When Edge 1 was throttled, the router detected the latency penalty and immediately shifted traffic to Edge 2 and Edge 3. When an edge was killed entirely, 100% of client requests succeeded through automatic failover."
